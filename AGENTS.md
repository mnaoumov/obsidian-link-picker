# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Link Picker is a folder-scoped, deterministically ranked note picker for Obsidian. It ships two faces deliberately:

- an **`Insert link...` editor command**, the user-facing half;
- a **callable API returning a string**, which is where the plugin came from — it is an extraction of a 568-line script (`LinkSuggester.ts`) in the author's personal vault whose 17 consumers are all Templater templates writing `<field>: <link>` into a note's properties. The extraction is done; publishing the API and shrinking that script to a shim is still ahead.

A command-only plugin would serve none of those consumers, which is why the API is not an afterthought.

## Architecture

- `src/item.ts` — **pure**. The item model, `SegmentMatchMode`, `applyQuery`, and the whole seven-tier ranking. No Obsidian API beyond the `TAbstractFile` type, so it is unit-tested directly; `src/item.test.ts` is the regression net for ranking behavior.
- `src/link-picker-modal.ts` — the `SuggestModal`. Folder navigation, the control strip and the hotkeys behind it, item construction from the vault. **`refreshSpellcheck` spell-checks the box while — and only while — it can NAME a note.** Obsidian builds every `SuggestModal` input with a hardcoded `spellcheck="false"` and never consults `Editor > Spellcheck`, which is right for a box that only FINDS a note and wrong for this one while `Create new` is on offer: `createNewAsync` takes `inputEl.value` verbatim as the new note's title, and only falls back to a `prompt` — which has always followed the setting — when the box is empty. It is keyed on the same `!shouldShowOnlyFolders && shouldAllowCreate` condition that guards `createNew`, so the attribute cannot disagree with whether the offer is actually being made, and it hangs off `update()` rather than `onOpen`, which is the single funnel every toggle and `navigateTo` already run through — so a mid-open switch into `Folders only` is tracked without a second call site. The read-and-apply itself is **not** this plugin's: it is `applySpellcheckMode` / `SpellcheckMode` from `obsidian-dev-utils`, and `refreshSpellcheck` only decides which mode this picker is in. Covered by `spellcheck.cross-platform.integration.test.ts`, which reads the ATTRIBUTE (not the IDL property, which reports a default for an element carrying none) across the toggle and with the vault setting both on and off — a single reading proves nothing, since `false` is indistinguishable from Obsidian's hardcoded value.
- `src/select.ts` — `select(params)` plus the two option shapes: `SelectOptions` (everything optional — an ALIAS of the published `LinkPickerApiSelectParams`, see below) and `SelectParams` (every default resolved, in the plugin internal vocabulary — what the modal reads).
- `src/link-picker-api.ts` — the whole published surface in one file: the contract version, the zod contract, and `LinkPickerApi`, which delegates to `LinkPickerComponent`. `plugin.ts` DECLARES it from `getPluginApis()` and lets `PluginBase` publish it — never by calling `publishPluginApi` by hand, which publishes the registry record but leaves the `obsidian-dev-utils:plugin-loaded` broadcast saying `apiVersions: []`, since the base derives that payload from the override alone. A third party following the published protocol holds no library copy and reads only that broadcast, so a hand-published API reads to them as no API at all.
- `api.d.ts` — at the repo ROOT, not in `src/`, because it is a distributed artifact rather than compiled source. Hand-written, and it imports from `obsidian` and NOTHING else: a consumer copies it whole, so an `obsidian-dev-utils` import in it would make them install the library this file exists to save them from. It holds the single declaration of the published surface — `LinkPickerApi`, `LinkPickerApiSelectParams`, and structural inlines of `PathOrFile`, `FolderNoteConfig`, `FolderNoteLocation` and `SegmentMatchMode` — which `src/link-picker-api.ts` implements rather than restates, and the README links rather than re-types.
- `src/link-picker-component.ts` — resolves `SelectOptions` into `SelectParams` from the plugin settings, and owns the minimal built-in `createNote`.
- `src/command-handlers/` — the editor command, which is the generic `Insert link...` when handed no picker and a configured picker's own command when handed one.
- `src/picker-commands-component.ts` — keeps one command registered per configured picker, disposing and re-registering the batch when the picker list changes.

## Deviations from the standard plugin architecture

The workspace convention is that all plugins share the same architecture; intentional deviations are documented here.

- **No `pluginNoticeComponent` use in the picker path.** Dismissing the picker rejects, and that is the user declining rather than a failure, so it produces no notice — see `insert-link-editor-command-handler.ts`.
- **The settings tab binds one array for six rows.** `bind` is keyed on a TOP-LEVEL settings property and a picker's fields are two levels down, so every picker row binds `pickers` itself and converts in both directions through `bindPickerProperty`. Bypassing `bind` would also bypass validation, the transformers and the debounced save.

## Things that are easy to get wrong

- **The prefix and suffix are DROPPED when the user declines a link**, unless `shouldApplyPrefixSuffixWhenNoLinkSelected` says otherwise. A dangling `"Person: "` with nothing after it is worse than an absent property key, so that is the default — but a document that needs the key present regardless can still ask for it. This replaced an `inlineField` option that hardcoded the `": "` separator AND always emitted it, so declining a link wrote `"Person: "`.
- **`prefix` is not a placeholder.** `inlineField` used to double as one, which is why a picker with no placeholder still showed a useful prompt. A prefix is output formatting — `"Person: "` is a bad prompt — so that fallback is gone, and a caller wanting both passes both.
- **`SelectOptions` is an ALIAS of `api.d.ts`'s `LinkPickerApiSelectParams`, and must not become a copy of it.** That is what makes the published file and the code one declaration rather than two that agree today. The consequence is that the caller-facing shape is spelled in the PUBLISHED vocabulary throughout the plugin: `folderNoteConfig.location` and `segmentMatchMode` are plain string unions, because `api.d.ts` may not import `obsidian-dev-utils` or reach into `src/`, and a string enum is NOMINAL in TypeScript — `'InsideFolder'` is not assignable to `FolderNoteLocation.InsideFolder` however identical the two are at runtime.
- **The conversion lives in `link-picker-component.ts`, once, in `FOLDER_NOTE_LOCATIONS` and `SEGMENT_MATCH_MODES`, and it is a TABLE rather than a cast on purpose.** `resolveOptions` is where a partial public shape becomes the fully resolved `SelectParams` the modal reads, so it is the natural place for it — and the tables' key types are derived FROM the enums with a template literal, so a member added, renamed or removed in `obsidian-dev-utils` or in `item.ts` fails to compile there. **That is the only compile-time tether `api.d.ts`'s inlined copies have**: `skipLibCheck` is on, so a root declaration file is never checked from the inside, and a cast here would let the published file go stale in silence. Do not simplify either table into an assertion.
- **`SelectOptions` carries no `app`, and must not grow one.** It is the shape the published API takes, and a consumer reaching across the plugin boundary must not have to hand the provider back the `App` the provider already holds. `LinkPickerComponent` fills it in from its own field.
- **The API's consumers are read STRUCTURALLY in the tests and the demo vault, never through `watchPluginApi`.** Two different reasons, both deliberate. `api.cross-platform.integration.test.ts` cannot use it because `lib` inside an `evalInObsidian` closure carries only the harness's base helpers unless the repo seeds the `obsidian-dev-utils` integration-test harness plugin, which cannot load on Android at all — and a structural read is the stricter test anyway, since a registry record is a wire format between different bundled library copies and a reader holding no copy is the case that proves it. `demoSetup.ts` cannot use it because a script in a vault has no bundler and no library copy. A consuming PLUGIN should still use `watchPluginApi`, which is what the README and note 06 show.
- **Folder navigation belongs in `selectSuggestion`, not `onChooseSuggestion`.** Obsidian closes the modal around `onChooseSuggestion`, and on MOBILE that close lands after anything the callback does — so re-opening from there, inline or on a later tick, just dismissed the picker. Navigating before the base class runs means the modal is never closed at all. It also keeps `isSelected` false while navigating, without which dismissing after a drill-in leaves the caller's promise pending forever.
- **The empty row is excluded by IDENTITY, not by type.** It is backed by the vault root, which is a folder, so a plain `isFolder` test sends `Alt + 1` navigating to the root instead of declining the link.
- **The vault root's path is `/`, not `''`.** Anything that assigns `folderPath` from a folder must normalize it, or the root reads as a folder with a parent and two characters to strip off every row.
- **Every hotkey handler returns a `boolean`, and `false` is the only value that consumes the key.** Obsidian types the character otherwise: unconsumed, `Alt + 3` also filters the list by `3`, and `Alt + 1` — which closes the picker — types into the note. So a handler returns `false` when it acted and `true` when it deliberately declined (`createNew` with creation turned off; the three that decline while showing only folders). Never return nothing: the library's `KeyboardCommand.onKey` is typed `boolean`, and one uniform convention is easier to hold than two.
- **The control strip is the picker's only affordance on mobile**, which is why it replaced Obsidian's instruction bar rather than joining it: an instruction bar can only name a key, and a phone has no `Alt` to press. Every control runs the same handler its hotkey does — `onActivate` and `onKey` on one command — so a behavior is never reachable one way and not the other.
- **The strip is `obsidian-dev-utils`', not ours.** `buildModalCommands` declares the six controls through `ModalCommandBuilder` from `obsidian-dev-utils/obsidian/modals/modal-command-builder` and builds them in `ModalCommandsRenderMode.Buttons`; `update` calls `refresh()` on the returned handle. The library owns the markup (`.modal-command`, `.modal-command-hotkey`, `is-active`, `aria-pressed`), the CSS — injected at runtime, which is why `src/styles/main.scss` carries no strip rules — the `mousedown` `preventDefault` that keeps a search alive under a click, suppressing the hotkey hint on mobile, and disabling rather than removing an unavailable control so the strip never reflows under a finger. **Do not reintroduce a local copy of any of that.** It also owns the hint FORMAT: `alt 1`, `shift ↵`, the library's, which is not what the prose in the README and demo vault writes (`Alt + 1`) — that is deliberate, since the prose names the key you press.
- **`build()` states the strip immediately, so it must be the LAST thing the constructor does.** It reads the toggle fields to set pressed and disabled state, and a chain hoisted above their assignment reads `undefined`.
- **Folder notes are `obsidian-dev-utils`', not ours.** Every folder-note question goes through `resolveFolderNote` / `resolveFolderNoteConfig` from `obsidian-dev-utils/obsidian/folder-note`, which reads the installed `folder-notes` plugin's live configuration. Do not reintroduce a hardcoded name — the original script hardcoded `!.md` in five places, and removing that was most of the extraction.
- **`isMatch` is the union of the two weakest tiers, on purpose.** An item is shown exactly when it ranks at all, so `isMatch` is `isIncludeEveryTerm || isSubsequenceEveryTerm` — computed once in `applyQuery` and shared with the tiers so the two cannot drift. That is also why `SegmentMatchMode.Fuzzy` ADDS a seventh tier rather than merely widening the match test: a shown item satisfying no tier would break the rule, and would silently lose the folders-lead tiebreak every tier applies.
- **`Fuzzy` finds more, it never reorders.** The six tiers above it all rest on equality, `startsWith` or `includes`, every one of which is strictly stronger than a subsequence, so the mode leaves them untouched — a scattered hit can only ever land below a contiguous one. Do not "improve" this by making the upper tiers fuzzy too: it would collapse the distinctions the tiers exist for, which is exactly what the plugin sorts into fixed tiers to avoid.
- **`updated` is compared as a string.** A frontmatter timestamp is ISO; the `stat.mtime` fallback is zero-padded to 13 digits so both sort under one `localeCompare`.
- **Comments must be one sentence per line.** `lint:fix` capitalizes the first word of every comment LINE, so a wrapped sentence comes back with a capital in the middle of it.

## Testing

- **`npm run test:coverage` is a gate, and it is 100 %.** `npm test` alone passing means nothing about it.
- **The integration suites share ONE Obsidian**, so each ends by picking something rather than by walking away — a picker left open is the next suite's first `.prompt`.
- **`06 Calling it from a script.md` must stay the LAST demo-vault note with buttons.** Its `Ask the API for a person link` button deliberately does not await `select` — a button that waited for you to pick would sit there until the suite's 15-second budget expired and fail — so it returns immediately and leaves the picker OPEN for a human to answer. The buttons suite walks notes in name order, and an open modal would block the next note's buttons. A `07` needs that button reworked, not merely appended after.
- **Drive a behavior by CLICKING its control, so the suite can be cross-platform.** The harness sends keys through Electron's input API, which Android does not have, so a suite that presses a key can only ever run on desktop. `hotkeys.desktop.integration.test.ts` is the one that deliberately does: it exists to prove the key is CONSUMED, which no click and no mocked scope can show.
- **Do not dispatch synthetic `KeyboardEvent`s** to work around that: they are untrusted, Obsidian may ignore them, and a lint rule refuses them. Reach the state through the product's own affordances instead.
- **The waiting happens in NODE, not inside an `evalInObsidian` closure — every suite here, without exception.** A single closure is capped at ~30 s by the transport (`commandTimeoutInMilliseconds` on desktop, `scriptTimeoutInMilliseconds` on Android), so a closure that waits dies at the cap and reports a bare `script timeout` naming the harness rather than the wait that overran. These suites carry five to seven waits each, so sizing the ceilings under the cap — the fix the sibling plugins took — would leave each wait three or four seconds, which is not enough for a picker to open on a cold phone. So each wait is its own `pollInObsidian`: a short `poll` closure reading one DOM predicate, an `until` evaluated in **Node** (where it can close over the stamped names the test already holds), and the long budget in `timeoutInMilliseconds`. Each instantaneous act — typing, clicking a row, clicking a control — is its own short `evalInObsidian`. `obsidian-dev-utils`' `no-over-cap-wait-in-eval-in-obsidian` fails `npm run lint` on any closure that goes back to the old shape.
- **Every wait gets 60 s — because Android sets the floor, not desktop, and Node's budget is one it can actually spend.** The suites were written against desktop, where 10 s is generous; on a *long-running* Android emulator the same waits sit right on the edge. `create-new-note` failed twice at `waitUntil timed out after 10000 milliseconds: the note exists`, and the four `Layout is ready after …ms` readings say why: `7072ms` on a freshly booted emulator, against `21276ms`, `26596ms` and `36126ms` on one that had been up for days. **The slow case is an AGED emulator, not a cold one** — a fresh boot is the fastest state, roughly 3–5×, which is the opposite of the intuition. A larger budget costs a passing run nothing, since a poll returns the moment its predicate holds. Do not lower it back on the grounds that desktop does not need it.
- **Three things deliberately stay whole inside ONE closure, and splitting any of them is a regression.** The trusted `pressKey` in `hotkeys.desktop`, with the `focus()` that must precede it — only Obsidian holds that `lib` helper, and a re-render between the two sends the key elsewhere. The type-read-decline step in `segment-match-mode`, whose broken-up query matches nothing under `Substring`, so there is no row to poll for and a re-render between the read and the decline would act on a state it never read. And every render settle: it guards a reading that is about to change, and **a settle guarding an assertion about something being ABSENT must stay inside its closure**, because polling for an absence that is already true accepts before the thing has had a chance to appear.
- **`api.cross-platform` carries its pending `select` on a `ContextId`.** `select` settles only once something has been picked, several host round trips after the call that opened the picker, so its promise cannot be awaited in the closure that started it. The `start` closure stashes it on the shared context and the answer is polled for from Node. `spellcheck` likewise holds the vault's original `spellcheck` setting in Node and restores it in a Node `finally` — strictly safer than an in-Obsidian one, since a transport failure mid-flow can no longer strand the vault on a setting it was never asked for.
- **Verify one suite with `npx vitest run --project=integration-tests:desktop <file>`**, which runs only the file named. `npm run test:integration:desktop` is the slower way to check the same thing.
- **If the Android suite starts timing out, restart the emulator before you touch a timeout.** Uptime is the variable; a fresh AVD took the same suite from 388 s to 231 s and from one failure to 10/10.
- **`npm run capture:control-strip` is the phone pass, and it is deliberately NOT part of `test:integration`.** The `capture-control-strip:android` project drives the picker on the `obsidian_test` emulator with the harness's TRUSTED mobile input — `lib.clickElement` for every tap, `lib.pressKey` for the query — and writes seven frames to `dist/control-strip/`. It exists because a synthetic `HTMLElement.click()` dispatches no `mousedown`, so no other suite can show what the control's `preventDefault` prevents. `*.android-capture.` matches none of the standard project globs, including the Android project's own `*.android.`, so a normal run never picks it up: it needs an emulator and it writes PNGs. Its frames are release-gate evidence for a human to look at, NOT listing material: they are full-screen device captures of intermediate states, several of which exist to show a control disabled.
- **The suite no longer hand-rolls `adb`, and the calibration it needed is gone by construction — do not reintroduce either.** It drove `adb shell input tap` / `adb shell input text` through `execFileSync` because when it was written the trusted helpers were desktop-only. Since `obsidian-integration-testing` 12.1.2 they are not: `clickElement` injects a CDP `Input.dispatchTouchEvent` pair into the WebView, which Blink expands into the same compatibility `mousedown` → `mouseup` → `click` a finger produces, and `pressKey` injects `Input.dispatchKeyEvent`. The four hand-rolled pieces map one-to-one onto harness exports — `tapDevice`-class touching onto `clickElement`, `screencap` onto `captureDeviceScreenshot`, `adb devices` + `emu avd name` onto `resolveEmulatorDeviceId` — so nothing in the file shells out any more. **The page-to-screen offset search is what that buys.** An `adb` tap speaks device pixels from the top of the SCREEN, so it needed `devicePixelRatio` and a status-bar offset that nothing in the page reports; the file used to FIND that offset by tapping candidates and seeing which one flipped a toggle. CDP takes CSS pixels in the WebView's own viewport — the space `getBoundingClientRect` already reports — so both terms disappear rather than being measured.
- **A converted tap that silently does nothing is the failure to rule out, and the suite rules it out itself.** Every tap is required to have an observable effect — `aria-pressed` flips, or the picker ends — and that effect arrives only at the END of the compatibility mouse sequence. So a touch that produced no `mousedown` could produce no click either, and the step fails instead of passing while proving nothing. That is what keeps the `preventDefault` proof from going vacuous: one tap has to flip `Subfolders` on AND leave the field focused with its query intact. The same mechanism is independently exercised by the listing suite, whose `closeAnyOpenPicker` taps a `.modal-command` with `clickElement` and waits for the picker to close.
- **`npm run capture:screenshots` writes the LISTING set, both halves, and the two legs run on different devices.** `capture-screenshots:desktop` writes `images/screenshots/screenshot-desktop-*.png` at 1200x800; `capture-screenshots:android` writes `screenshot-mobile-*.png` at 900x1600 — the size the community store asks for, taken on an AVD built at exactly that size (`obsidian_screenshots`), because there is no mobile equivalent of the desktop viewport override and the capture is always the device's own framebuffer. **Do not point it at the shared `obsidian_test` AVD**: that one is a Pixel 10 Pro XL at 1344x2992, and resizing a running AVD recreates the activity and with it the WebView the Appium session is attached to. The mobile frames are not a narrower copy of the desktop ones — the control strip is the picker's only affordance on a phone, so they show an interface the desktop frames do not have.
- **The mobile listing shots are taken with the soft keyboard UP, and raising it takes two things, not one.** The `obsidian_screenshots` AVD is built `hw.keyboard=yes`, so Android suppresses the on-screen keyboard and the picker's lower half captured as ~700px of empty modal — 45 % of the frame, a void no user ever sees. `settings put secure show_ime_with_hard_keyboard 1` is necessary and NOT sufficient: the picker's field takes focus programmatically, and a WebView does not ask for an IME without a gesture, so a run with the setting alone came back with the same empty band. A real `adb shell input tap` on the field is the gesture. **Both halves now come from `obsidian-integration-testing`** — `withSoftKeyboardEnabled` owns the setting and its exact restore, including restoring it to unset, and `raiseSoftKeyboard` owns the touch. The recipe was worked out here and moved there once ten sibling suites wanted it, so this suite is also its regression test: its two frames must reproduce, and they do.
- **Do not detect the keyboard through the viewport — nothing in the page moves.** `innerHeight`, `visualViewport` and even `.prompt` all stay at the full 800 with the keyboard shown and `dumpsys input_method` reporting `mInputShown=true`; Obsidian Mobile keeps a full-screen container and lifts its contents inside it. The one thing that moves is the search field, so how far it sits off the bottom is the signal — which is what the harness's `checkIsSoftKeyboardUp` reads. A failure dumps the device framebuffer to `dist/screenshots/` plus the `input_method` state, because this is not diagnosable from an assertion message. Note the signal only works for a field anchored to the BOTTOM, as this one is: for a centred modal the same test is true with no keyboard at all.
- **The mobile shots capture the DEVICE, not the web page.** `captureObsidianScreenshot` goes through Appium in the WebView context, so it photographs the page: no status bar, and no keyboard, because the IME is a system window. These shots use the harness's `captureDeviceScreenshot`, which reads the framebuffer as the control-strip pass does. That is also why these frames carry a status bar and the pre-keyboard ones did not.
- **The mobile frames ARE byte-reproducible, and it took three separate answers — every one of them found by capturing twice and diffing, not by reasoning.** A re-capture of an unchanged suite used to rewrite both PNGs with a different wall clock, a battery that had charged since the last run and a radio that came and went, so a capture always left a tree nobody could commit — and the second frame additionally carried a teal selection handle, a real defect in a store listing image rather than mere churn. **The status-bar band is PAINTED OUT** (the harness's `paintOutStatusBar`, given the 48px this AVD measures, compositing the background color it samples from the band's own empty rows), not pinned: SystemUI's demo mode held the clock at `12:00` and two runs still disagreed on 1823 full-contrast pixels, because the bar's leading group is laid out at a different offset between emulator boots. That is also why the suite writes no device settings of its own any more. **The handle is avoided by raising the keyboard while the field is EMPTY** and writing the query back afterwards, which `raiseSoftKeyboard` now does by itself (`shouldEmptyFieldForTouch`, on by default): the touch that raises the IME puts Chromium's insertion handle under the caret when it lands inside text, which is exactly why shot 2 carried one and shot 1 — whose query is empty — never did. Do not turn that option off; that is the bug. The geometry it returns is read with the field still empty, which `expectControlStripClearOfKeyboard` accepts because the strip and the field are both anchored to the bottom of the modal. **The caret itself is not painted** (`caret-color` on the field, `hideCaret`), because it blinks and there is no settle long enough to outwait a blink. That one stays in this suite on purpose: it is a presentation choice about this picker, where the other two are true of any device capture.
- **The painted band is bounded by an assertion, not by trust.** The harness's `paintOutStatusBar` requires the row just under the bar's content to be one flat color across the frame, so a taller status bar or an Obsidian that starts drawing higher fails the capture instead of quietly painting over the product.
- **Verify a change to any of that by capturing TWICE and comparing, never by looking at one frame.** Both PNGs must come back byte-identical between the two runs; a single green capture says nothing about reproducibility, which is the property the frames are committed on.
- **Two suites now share the `*.android-capture.` suffix, so the projects are routed by FILE, not by suffix.** They keep the shared suffix on purpose: it is what the author's other screenshot suites are called. It no longer buys an exemption: from `obsidian-dev-utils` 103.0.0 the shared ESLint config holds `*.android-capture.` files to `no-untrusted-input-events` like every other integration test, where earlier releases skipped them by filename. This repo is the only one with two Android capture projects, so `scripts/vitest-config.ts` includes `control-strip.android-capture.…` and `screenshots.android-capture.…` by name. Routing either project off the bare suffix runs each suite on the other's AVD, and the listing shots then fail their own size assertion — which is the good outcome; the bad one is the control-strip pass quietly overwriting nothing at all while the listing PNGs come out 1344x2992.
- **The host half of that suite must not use a bare `setTimeout`.** It runs in Node, but `obsidianmd/prefer-window-timers` cannot tell, and `lint:fix` will rewrite it to `window.setTimeout` — which typechecks and then throws `window is not defined`. Use `node:timers/promises`.
- **Use `lib.createNote` instead of `app.vault.create` for any note whose CONTENT matters.** The Android transport loses roughly 0.9 % of `vault.create` writes — the file lands 0 bytes while `TFile.stat` reports the full count, and it does not heal — so a content assertion fails as an unrelated-looking per-test flake. `createNote` writes, reads back, and repairs, and is harmless on desktop. The `Source-*.md` notes are the deliberate exception: they are created empty, so reading empty back proves nothing, and they stay on `app.vault.create`.

## Pending

- Released at `1.0.1` (`12f30f2`, tag `1.0.1`). Unreleased on `main` since it: the `obsidian-dev-utils` command-builder convergence, the `build:compile` wiring fix, the raised soft keyboard on the mobile listing shots, the configurable `segmentMatchMode` — which also took the API contract to `1.1.0`, so the release notes have to say so — the API moving from a hand-published record to a `getPluginApis()` declaration, which is what makes the `obsidian-dev-utils:plugin-loaded` broadcast name that `1.1.0` instead of announcing no API at all, and the published `api.d.ts` — the release notes should point a consumer at it, since it is the file they copy and it did not exist at `1.0.1`. The three pre-release items that pass carried are answered: the community-plugin survey found nothing comparable (7,135 registry entries; the record is in the task file), the control-strip pass now runs on the emulator under real touches (`npm run capture:control-strip`), and the live-vault recheck of the shim's `inlineField` → `prefix` mapping was replaced by end-to-end coverage of declining a link WITH a prefix, in `api.cross-platform.integration.test.ts`.
- `obsidian-dev-utils` was raised from `^103.2.0` to `^105.0.0` on `main`, crossing 102, 103 and 104 in one step. It is a `devDependency`, but the plugin source imports it and esbuild bundles it into `main.js`, so the raise ships and the release notes should say the bundled library moved. It carried 26 interface members from method to property style across 12 files — the shared config's `method-signature-style` returning to `property` — with no behavioral change, and it is what lets `no-soft-break-in-paragraph` be on in this repo at all.
- One finding from that pass is still open, and it is a styling question rather than a bug in behavior: **a toggle turned on while it still holds focus keeps the neutral fill**, so between the tap that turns it on and the next tap elsewhere the strip reads as though it were off. `aria-pressed` and `is-active` are both correct throughout — only the painted result is not.
- **The control-strip pass has not been re-run on a device since it was converted to the harness's trusted touches, so its seven frames are still the `adb` era's.** The conversion is green on everything that can be checked without a phone — compile, lint, `format:check`, spellcheck, `lint:md`, and the unit suite at 100 % — and the mechanism it now uses is already exercised on Android in this repo by the listing suite's `closeAnyOpenPicker`, which taps a `.modal-command` with `clickElement` and waits for the picker to close. What is outstanding is the run itself: `npm run capture:control-strip`, with the seven PNGs in `dist/control-strip/` read against a run from before the change. **The run is blocked by the machine rather than by this repo** — the harness probes a device's AVD over the emulator CONSOLE, so one unresponsive emulator belonging to any other project makes it refuse to start `obsidian_test` at all (`device emulator-XXXX did not answer 'adb -s … emu avd name' within 5000ms … so this run cannot tell whether it is already serving that AVD`). Its own remedy is to kill that device, which is not this repo's to kill. Retry when no foreign emulator is up.
